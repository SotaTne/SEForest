# Test and Report

`Forest_Program/` 以下の実装コードとテストコードを対象に、テスト作業と
`Forest_Document/TestSpecification/index.html` の更新を支援する。

## 基本原則

- `Forest_Program/` 以下のコードだけをテスト判断の根拠にする。
- 要求仕様書や設計書との整合性確認は行わない。
- `Forest_Document/Program/index.html` と `Forest_Document/TestResult/index.html` は変更しない。
- コードまたはHTMLを変更する前に、何をどう変更するか文章で提案し、ユーザーの承認を得る。
- テスト実行はユーザーの依頼と会話の文脈から判断してよい。
- 実行したテストに対応する箇所だけを記録する。
- ユーザーが全件更新を明示した場合だけ、回帰テスト結果を全項目へ反映する。
- 不明、未確認、間接的に正しそうという状態を `良好` と記録しない。

## ワークフロー

### 1. 対象を調査する

1. `Forest_Program/` 以下の実装、テスト、テスト設定、標準実行コマンドを確認する。
   標準コマンドはプロジェクトルートの `mise.toml` を優先して確認する。
2. 実装変更時は、クラス図またはコード構造から依存関係を追跡する。
3. 変更対象から完全に分離されているクラスやテストは影響範囲から除外する。
4. テスト変更時は、変更されたテスト自身を対象とする。

### 2. 実行前にレビューする

次の観点で既存テストを確認する。

- 正常系
- 異常系
- 境界値
- テスト間の独立性
- 再現性
- 実装との一致
- 変更された実装に依存するテストの不足
- 属性とメソッドの検証漏れ

問題または不足を見つけた場合は、内容と影響をユーザーへ報告し、今回解決するか
意図的に無視するか判断を求める。無視すると決まった問題は文書へ記録しない。

テストが成功しても、カバレッジ不足、弱い検証、暗黙の前提などがあれば報告し、
`良好` と記録してよいかユーザーの判断を求める。

### 3. 不足テストを扱う

- 不足テストを勝手に作成しない。
- まず必要なテストと確認内容を提案する。
- ユーザーが作成を依頼し、提案を承認した後にテストコードを追加する。
- ユーザーが自分で作成すると決めた場合は、追加後の指示を待つ。

### 4. テストを実行する

- プロジェクトに既存の標準テストコマンドがあれば、それを優先する。
  このプロジェクトでは原則としてプロジェクトルートから `mise run test` を使う。
- テスト前の静的確認が必要な場合は、プロジェクトルートから `mise run check`、
  `mise run typecheck`、`mise run check:html` の利用を検討する。
- Python 環境の依存関係が未セットアップの場合は、勝手に `mise run setup` や
  `mise run setup:python` を実行せず、ユーザーに確認する。
- 標準コマンドが判別できなければユーザーへ確認する。
- 実装変更時は、変更箇所に依存するテストの実行を提案する。
- ユーザーが実行しないと決めたテストは記録対象にしない。
- 環境や依存関係が不足している場合、勝手にインストールしない。原因と必要な操作を報告する。
- 外部サービスへの書き込みなど、副作用または破壊性があるテストは実行前に確認する。

### 5. 文書更新案を提示する

テスト仕様または結果を反映する前に、次を文章で説明して承認を得る。

- 更新するクラス、属性、メソッド、テストケース
- 追加または変更する説明
- 記録するテスト種別と結果

### 6. TestSpecificationを更新する

承認後、`Forest_Document/TestSpecification/index.html` の対応箇所だけを更新する。

#### 属性表

既存形式を保つ。

```text
属性（インスタンス変数） | 束縛 | 分類 | 説明 | テスト結果
```

- クラス属性やモジュール定数ではなく、インスタンス属性だけを掲載する。
- インスタンス属性は `__init__` で定義されていなければならない。
- `__init__` 以外で属性の新規生成を見つけた場合は、文書を更新せず、実装上の問題として報告する。
- Pythonの命名に応じて `public`、`protected` (`_name`)、`private` (`__name`) と分類する。
- 各属性に検証を用意する。公開APIから状態を明確に観測できる場合は、その方法で検証してよい。
- 属性が観測不能な場合は、実装を勝手に変えず検証方法をユーザーと相談する。
- 同じ属性に複数ケースがある場合は、属性名、束縛、分類のセルを `rowspan` で結合し、説明と結果をケースごとに分ける。

#### メソッド表

「分類」の直後に「テスト種別」を置く。

```text
メソッド（操作） | 応答 | 分類 | テスト種別 | 説明 | テスト結果
```

- 対象クラス自身が定義またはオーバーライドしたメソッドを掲載する。
- 継承しただけのメソッドは掲載しない。
- `__init__`、特殊メソッド、プロパティ、static method、class methodを含め、クラス内で定義したメソッドは原則掲載する。
- オーバーロード相当の各シグネチャまたは各分岐は、それぞれ記載する。
- テスト種別は `単体テスト`、`結合テスト`、`操作テスト`、`性能テスト` から選ぶ。
- 結合テストは主対象となるクラスまたはメソッドを決め、説明に連携対象を明記する。
- 同じメソッドに複数ケースがある場合は、メソッド、応答、分類のセルを `rowspan` で結合し、テスト種別、説明、結果をケースごとに分ける。
- 説明には、メソッドの振る舞いと何を確認するテストなのかが分かる内容を書く。
- `Forest_Document/Program/index.html` に対応アンカーが存在する場合だけリンクし、存在しない場合はリンクなしの `<code>` とする。

#### 結果表記

- 成功: `良好（YYYY年M月D日）`
- 失敗: `失敗（YYYY年M月D日：短い原因）`
- 意図的な未実施: `未実施（YYYY年M月D日：理由）`
- 意図的な保留: `保留（YYYY年M月D日：理由）`

結果は最新の内容へ置き換え、過去の結果はGitなどの履歴に任せる。単に実行対象外だった項目は
更新しない。

複数ケースを一行へ集約せず、ケースごとに結果を記録する。

内容を変更した日は、フッターの `Updated` を同じ日付へ自動更新する。`Created` は変更しない。

## 完了条件

次を満たした時に作業完了とする。

- 対象テストのレビューと必要な実行が完了している。
- ユーザーが承認した変更だけを反映している。
- 実行したテストに対応する `Forest_Document/TestSpecification/index.html` の箇所を更新している。
- フッターの `Updated` を更新している。
- 未解決事項があれば、完了報告に明記している。
